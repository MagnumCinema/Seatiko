# Кабинет владельца ресторана

Этот документ фиксирует отдельный бизнес-контур FoodAssistant для владельцев ресторанов. Клиентские сценарии гостя остаются в мобильном приложении; сайт используется для подключения бизнеса и работы с заведением.

## 1. Роли и каналы

| Роль | Основной канал | Что доступно |
|------|----------------|-------------|
| Гость | Мобильное приложение | Карта, заведения, бронирование, QR-сессия, заказ, история заказов и броней |
| Владелец ресторана | Web-кабинет | Подключение заведений, статус модерации, брони ресторана, история изменений |
| Менеджер / персонал | Web + staff-app, следующий этап | Зал, меню, стоп-лист, вызовы, статусы заказов, check-in |
| Администратор платформы | Web-admin | Проверка заявок, возврат на доработку, одобрение и публикация |

Аккаунт владельца и аккаунт гостя не смешиваются. Один владелец может добавить несколько ресторанов и переключаться между ними в кабинете.

## 2. Подключение ресторана

```text
[Страница «Для бизнеса»]
        ↓
[Регистрация владельца]
  имя, фамилия, рабочий email, пароль
        ↓
[Кабинет → новый черновик ресторана]
        ↓
[Заполнение обязательных данных]
  название и описание
  адрес и координаты точки на карте
  кухня и часы работы
  телефон и email заведения
  минимум одна фотография
        ↓
[Отправка на модерацию]
        ↓
[Проверка платформы: 1–3 рабочих дня]
        ├── возврат с комментарием → редактирование → повторная отправка
        └── одобрение → публикация
        ↓
[Ресторан автоматически появляется точкой на карте]
        ↓
[Кабинет начинает показывать бронирования заведения]
```

Гость не участвует в этом процессе. Его регистрация выполняется в клиентском приложении в момент защищённого действия: бронирования, заказа, уведомления или подтверждения прихода.

## 3. Статусы и права редактирования

| Статус | Значение | Владелец может редактировать |
|--------|----------|------------------------------|
| `DRAFT` | Черновик профиля | Да |
| `SUBMITTED` | Заявка ожидает проверки | Нет |
| `UNDER_REVIEW` | Модератор проверяет данные | Нет |
| `REJECTED` | Нужна доработка по комментарию | Да; первое изменение возвращает заявку в `DRAFT` |
| `APPROVED` | Профиль одобрен | Нет |
| `PUBLISHED` | Заведение опубликовано | Нет в MVP; изменения опубликованного профиля должны идти отдельной заявкой на изменение |

Переход к `SUBMITTED` разрешён только для полного профиля. Backend, а не только интерфейс, проверяет обязательные поля, корректный email, допустимые координаты, ценовой уровень и наличие фотографии.

## 4. Структура кабинета владельца

### Обзор

- статус ресторана и объяснение следующего шага;
- процент готовности профиля;
- путь подключения от черновика до карты;
- будущие и все бронирования;
- количество фотографий и дата последнего изменения;
- комментарий модератора при возврате заявки.

### Профиль заведения

- название, описание и кухня;
- адрес и координаты маркера;
- часы работы, телефон и email;
- ценовой уровень и средний чек;
- фотографии с отдельной обложкой;
- сохранение черновика и отправка на модерацию.

### Бронирования

- предстоящие, завершённые и все записи;
- дата и время, номер стола, количество гостей;
- имя и контакт гостя;
- статус `CONFIRMED`, `CHECKED_IN`, `CANCELLED` или `NO_SHOW`.

Владелец получает только бронирования своих опубликованных заведений. До публикации раздел показывает понятное пустое состояние.

### История действий

Журнал является append-only: записи добавляются автоматически и не редактируются из кабинета.

Фиксируются:

- создание черновика;
- изменённые поля профиля;
- добавление и удаление фотографий;
- отправка на модерацию;
- начало проверки;
- одобрение или возврат с комментарием;
- публикация ресторана.

Каждая запись содержит время, автора, роль, тип действия, список изменённых полей и комментарий модератора при наличии.

## 5. Безопасность и разделение данных

- restaurant API защищён JWT и проверкой роли `restaurant` / `admin`;
- владелец не может открыть заявку или журнал другого владельца;
- список броней строится по `venue_id`, связанным с опубликованными заявками владельца;
- email гостя доступен только в защищённом owner-контуре и используется для обслуживания брони;
- решение модератора и публикация доступны только роли `admin`;
- фотографии проверяются по типу и размеру; лимит — 8 файлов по 5 МБ.

## 6. Реализовано и следующий этап

### Реализовано в текущем MVP

- отдельная регистрация владельца на сайте;
- несколько ресторанов в одном аккаунте;
- полный lifecycle заявки и модерации;
- автоматическая публикация ресторана на общей карте;
- owner-dashboard с готовностью профиля;
- owner-facing бронирования;
- защищённый журнал действий;
- адаптивный интерфейс для desktop, tablet и mobile web.

### Следующий операционный этап

1. Схема зала с drag-and-drop столами.
2. Меню, категории, модификаторы и стоп-лист.
3. Правила бронирования: интервалы, hold time, депозит, предзаказ.
4. QR-коды столов и тестовый режим.
5. Роли сотрудников и приглашения в команду.
6. Live-очередь броней, вызовы официанта и статусы заказов.
7. Аналитика загрузки, среднего чека, отмен и no-show.
8. Отдельный процесс изменения уже опубликованного профиля без снятия ресторана с карты.

## 7. API текущего MVP

| Метод | Endpoint | Назначение |
|-------|----------|------------|
| `POST` | `/api/v1/restaurant/applications` | Создать черновик ресторана |
| `GET` | `/api/v1/restaurant/applications` | Список ресторанов владельца |
| `GET` | `/api/v1/restaurant/applications/:id` | Получить профиль |
| `PATCH` | `/api/v1/restaurant/applications/:id` | Сохранить разрешённые изменения |
| `POST/DELETE` | `/api/v1/restaurant/applications/:id/photos` | Добавить или удалить фото |
| `POST` | `/api/v1/restaurant/applications/:id/submit` | Отправить полный профиль на проверку |
| `GET` | `/api/v1/restaurant/applications/:id/activity` | Получить журнал действий |
| `GET` | `/api/v1/restaurant/reservations` | Получить брони ресторанов владельца |

> Текущий backend использует in-memory store для MVP. Перед production нужны постоянная БД, миграции, object storage для фотографий, pagination, retention policy и резервное копирование audit log.
