## Задачи

### 1. Предзаказ блюд к брони — **Открыто**

**Контекст.** На странице меню гость собирает «Ваш выбор» (порции и сумма). Список хранится только в `localStorage` на устройстве и **не отправляется** в ресторан. Ссылка с подтверждения брони (`?preorder=1&table=…`) уже ведёт на меню, но это только подсказка гостю.

**Нужно на бэке (по `APP_LOGIC` §5.3 / §8.4):**

- [ ] Привязать позиции меню к брони (`reservation_id` + `menu_item_id` + `qty` + цена на момент заказа).
- [ ] API: создать / изменить / отменить предзаказ к своей брони; отдать предзаказ вместе с бронью (гость, владелец, staff).
- [ ] Учитывать стоп-лист, удаление блюда, смену цены; алкоголь и прочие `requires_age_18` — только при `adult_preorder_allowed` (задача 5).
- [ ] Опционально: флаг ресторана «готовить к приходу» / «после посадки» (уже есть идея в APP_LOGIC).
- [ ] Уведомление кухне / staff при новом или изменённом предзаказе.

**Сейчас на фронте:** `seatiko_menu_selection:<venueId>` в `localStorage`; на странице явно написано, что список в ресторан не уходит.

### 2. `GET /api/v1/availability` — **Открыто**

Пилот: `/book` считает свободные слоты в браузере (`venue-availability.ts`) по `GET /venues`, затем для каждого ресторана `/tables` и `/schedule` (1 + 2·N запросов). После редизайна `/book` (2026-11-16) клиентский расчёт **остался** — нужен серверный endpoint.

Целевой контракт и требования — в [`ENGINEERING.md`](./ENGINEERING.md) § «Поиск свободных столов». После внедрения клиентская логика остаётся только для отображения.

### 3. Избранное ресторанов на сервере — **Сделано**

Поля `favorite_venues` на `User`, обновление через `PATCH /me` (`handlers` + `store`). Фронт кабинета синхронизирует список после логина (коммит `b5652ea4` и дальше в `main`).

### 4. Аллергии / диета в профиле — **Сделано**

Поля `diet_preferences` на `User` + `PATCH /me`. Фронт пишет/читает с API (тот же поток, что избранное).

### 5. 18+ и предзаказ возрастных позиций — **Открыто**

По `APP_LOGIC` §8.4:

- [ ] Поля `adult_preorder_allowed` (+ метаданные кто/когда/где подтвердил) на пользователе.
- [ ] Staff API: grant / revoke после проверки документа; журнал.
- [ ] В меню предзаказа скрывать/блокировать `requires_age_18`, если флага нет.
- [ ] Повторная проверка при подаче алкоголя.

Без этого задача 1 не должна открывать алкоголь в предзаказ.

### 6. Реальные способы оплаты — **Открыто**

В кабинете гостя сейчас заглушки. Нужен платёжный провайдер (или явный «оплачу в ресторане» без карты) по правилам APP_LOGIC.

### 7. Координаты демо-ресторанов — **Открыто**

Метки на карте «Как добраться» иногда не совпадают с адресом (например Beermaster Pub). Поправить `lat`/`lng` в сиде (`memory.go` / демо-данные) и при необходимости backfill в persistence, как для меню.

### 8. `free_tables: 0` в ответе map places — **Открыто**

У `MapPlace.FreeTables` (и части числовых полей) стоит `json:",omitempty"`. При 0 свободных столов ключ пропадает из JSON, попап карты может не показать «0 столов», хотя бронь всё ещё доступна. Убрать `omitempty` у `FreeTables` (как у `Venue.FreeTables`) или явно отдавать `0`.

### 9. Локали EN/RO для Google-only мест — **Открыто**

Поиск Places сейчас запрашивается с `languageCode: "ru"`, имя/адрес копируются во все три локали. Для EN/RO пользователи видят русские подписи у мест вне базы. Нужен запрос/кэш по локали гостя или отдельные поля.

### 10. Discover AI (NL → prefs / ranked venues) — **Открыто**

На `/discover` сейчас честный UI-стаб: поле ввода + ответ «скоро», без вызова модели. Endpoint `POST /api/v1/discover/ai` уже есть в клиенте (`discoverAi`), но полноценного контракта под NL→фильтры/ранжирование нет.

**Нужно на бэке:**

- [ ] Принять свободный текст (+ опционально city_id / текущие prefs).
- [ ] Вернуть структурированные preferences и/или ranked venue ids с объяснением.
- [ ] Стабильный fallback без LLM (правила/теги), чтобы UI не ломался при ошибке модели.

**Сейчас на фронте:** stub в `guided-chat.tsx`; `discoverAi` используется в legacy `app-shell`, не на `/discover`.

### 11. Live count «Найдено: N» для discover — **Открыто**

`ActiveFiltersBar` на `/discover` показывает снимаемые чипы фильтров, но без счётчика совпадений. Клиентский подсчёт по уже загруженной карте возможен, но для точности и пустых штатов лучше серверный count (или поле в `GET /map/places` / discover).

- [ ] Endpoint или расширение map/places: `total` / `matched` при тех же filter query params, что encode prefs.
- [ ] Контракт для empty state («0 мест — ослабьте фильтры»).

**Сейчас на фронте:** счётчик сознательно не показываем до этой задачи.
